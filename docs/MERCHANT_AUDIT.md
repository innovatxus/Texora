# Merchant portal — Phase 0 audit

**Date:** 2026-10-20 · **Source prompt:** `MERCHANT_PORTAL_BUILD_PROMPT.md`
**Baseline:** storefront Phases 0–8 (including the back office) on `feat/phase-8-back-office`.

This audit checks every piece the merchant prompt expects to build on, lists gaps and conflicts, and records the decisions taken before any merchant code is written. Each decision is also logged in `docs/DECISIONS.md` (D-060–D-071).

Merchants must never see the back office                                                       | `VENDOR` = `CUSTOMER` permissions + vendor/merchant permissions; it leaves `STAFF_ROLES`; merchant sign-in lands in `/merchant`. | C3  | **Pickup.** The prompt has a "pickup point" location type, pickup fields, "at least one location must ship or offer pickup", and PDP pickup availability                                      | **Removed** at the owner's request (platform-wide since D-044, confirmed for merchants on 2026-10-19). | C4  | Merchant location stock in `stockByLocation` (`m_{shopId}_{locationId}`) vs. a storefront that sells only `online` stock                                                                      | Merchant products sell from the sum of the merchant's ship-from locations. ## 4. How merchant data fits the storefront

- **Visibility:** a product is shown only if `status == "live"` **and** its shop is approved. Approval and suspension rewrite the denormalised `shop` field and product visibility in a batch, then revalidate `products`, `shops` and `shop:{slug}`, so suspended products disappear within one revalidation.
- **Caching:** storefront pages stay static with tag revalidation. The portal is request-time (`connection()` via `getSession`).
- **Stock:** see C4. Reservations and checkout don't change.
- **Search:** listing products gain shop fields; the shop facet appears only when more than one shop is in the result set.
- **Orders:** each line records its `vendorId` and shop name. Merchants read orders through a server query on `vendorIds`, and only their own lines are rendered.

## 5. Phase plan check

All nine phases of the prompt are kept, with these adjustments:

- **Phase 1:** also builds the rate limiter (G1) and the role change (C1/C2). The enum extensions (G3–G5) land here so later phases share them.
- **Phase 2:** builds password reset and verification email templates in the existing React Email set.
- **Phase 3:** integration tests add the Storage emulator (`--only firestore,auth,storage`).
- **Phase 4:** no pickup (C3); geocoder per D-068.
- **Phase 8:** adds the bundle budget script (G9).

## 6. Risks

- **Emulator ports:** live development and the integration suite share 8080/9099/9199. Tests must run with the live emulators stopped (unchanged from earlier phases).
- **Matrix size:** colours × fits × sizes can exceed 500 rows (e.g. 10 × 4 × 15). The grid is virtualised; the server caps variants per product at 600 (config).
- **Firestore document size:** drafts with 12 images × many colours stay well under 1 MiB because media is referenced by id.
